# Phân quyền bằng `[HasPermission]` trong ASP.NET Core

JWT Bearer xác thực người gọi bằng access token. Authorization dùng thông tin của người gọi để quyết định họ có được thực hiện action hay không. Trong INuStore, `GET /api/v1/User/GetAllUsers` yêu cầu quyền `User::GetAllUsers`. [UserController.cs](../src/INuStore.API/Controllers/UserController.cs)

## Dùng `[HasPermission]`

```csharp
[HasPermission("User::GetAllUsers")]
```

Mỗi đối số là một tên permission đầy đủ trong database. Attribute cắt khoảng trắng ở hai đầu tên và báo lỗi cấu hình nếu danh sách trống hoặc có tên rỗng. Tên quyền được so sánh theo `StringComparer.Ordinal`, có phân biệt chữ hoa và chữ thường. [HasPermissionAttribute.cs](../src/INuStore.API/Authorization/HasPermissionAttribute.cs) · [PermissionAuthorizationHandler.cs](../src/INuStore.API/Authorization/PermissionAuthorizationHandler.cs)

1. Gán permission `User::GetAllUsers` cho một role mà người dùng đang có.
2. Đăng nhập lại qua `POST /api/v1/Auth/Login` để nhận access token mới.
3. Gọi `GET /api/v1/User/GetAllUsers` với header `Authorization: Bearer <access-token>`.

| Kết quả | Điều kiện |
| --- | --- |
| `401 Unauthorized` | Request thiếu access token hợp lệ. |
| `403 Forbidden` | JWT hợp lệ nhưng người dùng thiếu quyền yêu cầu. |
| `200 OK` | JWT có quyền yêu cầu và action xử lý thành công. |

Các request mẫu nằm trong [INuStore.API.http](../src/INuStore.API/INuStore.API.http).

## ASP.NET Core kiểm tra quyền ở đâu?

Sau khi xác thực mật khẩu, [AuthService](../src/INustore.UseCase/UseCases/V1/AuthService/AuthService.cs) gọi `GetByUserIdAsync` nếu người dùng có role. Truy vấn tìm các permission được gán qua các role của người dùng. Sau đó service thêm một claim `Permissions` cho mỗi quyền vào access token. Claim là thông tin gắn với danh tính, ở đây giá trị của claim là tên permission. [PermissionRepository.cs](../src/INuStore.Infrastructure/Repositories/PermissionRepository.cs)

Khi request đến endpoint có `[HasPermission]`, JWT Bearer xác thực access token. Authorization middleware đánh giá các requirement của endpoint trước khi action chạy.

| Thành phần | Trách nhiệm |
| --- | --- |
| `HasPermissionAttribute` | Khai báo điều kiện trên controller hoặc action. Attribute kế thừa `AuthorizeAttribute` và tạo một `PermissionRequirement` chứa danh sách tên quyền. |
| `IAuthorizationRequirementData` | Cho framework lấy điều kiện từ metadata của endpoint. ASP.NET Core gọi `GetRequirements()` và thêm requirement trả về vào authorization policy. |
| `PermissionRequirement` | Giữ dữ liệu cần kiểm tra, cụ thể là danh sách tên quyền mà endpoint chấp nhận. |
| `PermissionAuthorizationHandler` | Đọc claim từ các identity đã xác thực trong `context.User`. Nếu có tên khớp, gọi `context.Succeed(requirement)` để đánh dấu điều kiện đã đạt. |

Handler chỉ đọc claim trong bộ nhớ. Khi thiếu quyền, handler trả về mà không gọi `Succeed`. ASP.NET Core yêu cầu mọi requirement trong policy đều đạt trước khi cho request đi tiếp. [PermissionRequirement.cs](../src/INuStore.API/Authorization/PermissionRequirement.cs) · [Microsoft Learn về custom authorization trong MVC](https://learn.microsoft.com/en-us/aspnet/core/mvc/security/authorization/custom-authorization-policies-with-iauthorizationrequirementdata-in-mvc?view=aspnetcore-10.0) · [Microsoft Learn về authorization policies](https://learn.microsoft.com/en-us/aspnet/core/security/authorization/policies?view=aspnetcore-10.0)

| Khai báo | Điều kiện |
| --- | --- |
| `[HasPermission("A", "B")]` | A **hoặc** B. Một requirement chứa hai tên và handler dùng `Any`. |
| `[HasPermission("A")]` và `[HasPermission("B")]` | A **và** B. Hai attribute tạo hai requirement, kể cả khi một attribute nằm trên controller và một attribute nằm trên action. |

`A` và `B` minh họa hai tên permission đầy đủ.

## Tự viết một rule với `[RequireDepartment("Sales")]`

Ví dụ minh họa một endpoint dành cho phòng Sales. Endpoint khai báo phòng ban cần có, còn handler đọc claim `department` để xác định phòng ban của người gọi. Để dùng ví dụ này, bổ sung dữ liệu phòng ban từ nguồn phía server vào access token khi đăng nhập thành công.

```csharp
using Microsoft.AspNetCore.Authorization;

namespace INuStore.API.Authorization;

public sealed class RequireDepartmentAttribute(string department)
    : AuthorizeAttribute, IAuthorizationRequirementData
{
    public IEnumerable<IAuthorizationRequirement> GetRequirements()
    {
        yield return new DepartmentRequirement(department);
    }
}

internal sealed record DepartmentRequirement(string Department)
    : IAuthorizationRequirement;

internal sealed class DepartmentAuthorizationHandler
    : AuthorizationHandler<DepartmentRequirement>
{
    protected override Task HandleRequirementAsync(
        AuthorizationHandlerContext context,
        DepartmentRequirement requirement)
    {
        var belongsToDepartment = context.User.Identities
            .Where(identity => identity.IsAuthenticated)
            .SelectMany(identity => identity.Claims)
            .Any(claim => claim.Type == "department"
                && string.Equals(claim.Value, requirement.Department, StringComparison.Ordinal));

        if (belongsToDepartment)
        {
            context.Succeed(requirement);
        }

        return Task.CompletedTask;
    }
}
```

Đăng ký handler trong `AddAuthorizationApi`, cùng chỗ đăng ký `PermissionAuthorizationHandler`. Handler trong ví dụ chỉ đọc claim và có thể dùng lifetime `Singleton`. [JwtExtensions.cs](../src/INuStore.API/DependencyInjection/Extensions/JwtExtensions.cs) · [Microsoft Learn về đăng ký handler](https://learn.microsoft.com/en-us/aspnet/core/security/authorization/policies?view=aspnetcore-10.0#handler-registration)

```csharp
services.AddSingleton<IAuthorizationHandler, DepartmentAuthorizationHandler>();
```

Gắn `[RequireDepartment("Sales")]` lên action. Token hợp lệ có `department=Sales` thỏa điều kiện. Token hợp lệ có `department=Support` hoặc thiếu claim nhận `403`. Khi thiết kế rule tiếp theo, xác định giá trị endpoint yêu cầu, nguồn dữ liệu đáng tin cậy và điều kiện để gọi `Succeed`.

## Best practices cho production

- Chọn thời hạn access token phù hợp với khoảng trễ thu hồi quyền chấp nhận được. INuStore đưa quyền vào token khi đăng nhập, nên token đã phát vẫn mang quyền cũ đến khi hết hạn. Nếu cần thu hồi quyền ngay, thiết kế thêm cơ chế kiểm tra trạng thái quyền hoặc thu hồi token phía server.
- Nếu điều kiện phụ thuộc vào từng bản ghi, chẳng hạn người gọi phải sở hữu đơn hàng, tải bản ghi rồi gọi `IAuthorizationService.AuthorizeAsync` với bản ghi đó làm resource trước khi đọc dữ liệu nhạy cảm hoặc ghi thay đổi. [Microsoft Learn về resource-based authorization](https://learn.microsoft.com/en-us/aspnet/core/mvc/security/authorization/resource-based?view=aspnetcore-10.0)

## Câu hỏi phỏng vấn senior

1. Bạn chọn lưu quyền trong JWT hay kiểm tra quyền qua database ở mỗi request dựa trên yêu cầu nào?
2. Bạn xử lý thu hồi quyền ngay thế nào khi access token cũ vẫn còn hiệu lực?
3. Bạn thiết kế thế nào để điều kiện trên controller và action kết hợp đúng theo nghiệp vụ?
4. Khi đổi tên permission đã được dùng ở nhiều endpoint, bạn triển khai thay đổi theo thứ tự nào để giảm gián đoạn?
5. Khi nào bạn chuyển từ kiểm tra claim sang resource-based authorization để kiểm tra quyền sở hữu?
6. Bạn sẽ kiểm thử những trường hợp nào để phân biệt lỗi xác thực, thiếu quyền và lỗi xử lý trong action?
