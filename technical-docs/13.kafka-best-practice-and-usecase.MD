# **Apache Kafka từ Fresher đến Senior – Hướng dẫn dành cho .NET Developer**

Mình sẽ giải thích Kafka theo hướng **hiểu bản chất → hiểu cách hoạt động → tự triển khai bằng .NET → áp dụng best practice production → xử lý các bài toán senior**.

Ví dụ xuyên suốt là một hệ thống thương mại điện tử dùng **ASP.NET Core Web API, SQL Server, Kafka và .NET Worker Service**, tổ chức theo Clean Architecture.

## **Phần 1. Kafka là gì? Tại sao cần Kafka?**

### **1.1. Kafka là gì?**

LEVEL 1 · FRESHER

**Apache Kafka** là một nền tảng distributed event streaming, được thiết kế để lưu trữ và truyền dữ liệu sự kiện (event) giữa các hệ thống với khả năng xử lý lượng dữ liệu lớn.

Nói đơn giản:

Thay vì Service A gọi trực tiếp Service B để thực hiện tất cả công việc, Service A có thể gửi một event vào Kafka. Những service quan tâm đến event đó sẽ tự đọc và xử lý.

Ví dụ khi một khách hàng đặt hàng thành công, hệ thống cần:

- Gửi email xác nhận đơn hàng.
- Trừ số lượng sản phẩm trong kho.
- Cập nhật báo cáo doanh thu.
- Gửi thông báo đến người dùng.

**Cách 1: Không sử dụng Kafka**

**Order API**

Gọi trực tiếp từng service

HTTP / REST / gRPC

Email Service

Inventory Service

Reporting Service

Vấn đề có thể phát sinh:

- Email Service bị lỗi hoặc chậm có thể ảnh hưởng đến luồng đặt hàng nếu API phải chờ.
- Order API phải biết cách gọi các service liên quan.
- Khi thêm một service mới, có thể phải sửa code của Order API.
- Nếu service đích không hoạt động, cần tự thiết kế cơ chế retry, lưu request chưa xử lý và phục hồi.

**Cách 2: Sử dụng Kafka**

**Order API (Producer)**

Publish OrderCreated event

**Apache Kafka**

Event 1

Event 2

Reporting Consumer

Luồng xử lý:

1. Order API tạo đơn hàng thành công.

3. Kafka lưu event.
4. Email Service đọc event để gửi email.

Các consumer có thể chạy độc lập và không nhất thiết phải xử lý event ngay tại thời điểm Order API publish.

**Điểm quan trọng:** Kafka không tự động giải quyết vấn đề đồng bộ dữ liệu hoặc transaction. Chúng ta vẫn cần thiết kế đúng cách để không mất event hoặc xử lý lặp.

## **Phần 2. Kiến trúc Kafka hoạt động như thế nào?**

LEVEL 1–2 · FRESHER → MIDDLE

Trước khi viết code, bạn cần hiểu sáu khái niệm:

| Thành phần     | Chức năng                                     |
| -------------- | --------------------------------------------- |
| Producer       | Gửi message vào Kafka                         |
| Broker         | Server lưu trữ và phục vụ message             |
| Topic          | Nhóm các message cùng chủ đề                  |
| Partition      | Phân chia topic để lưu trữ và xử lý song song |
| Consumer       | Đọc message từ Kafka                          |
| Consumer Group | Nhóm consumer phối hợp xử lý message          |

### **2.1. Producer**

Producer là application gửi message vào Kafka.

Trong .NET, Producer có thể là ASP.NET Core Web API hoặc Background Worker.

Ví dụ về message:

```
{
  "eventId": "evt-001",
  "orderId": 1001,
  "userId": 25,
  "totalAmount": 500000,
  "occurredAt": "2026-11-23T10:00:00Z"
}
```

Producer quyết định gửi message vào topic nào và có thể cung cấp message key để Kafka xác định partition.

### **2.2. Topic**

Topic giống như một danh mục chứa các event cùng loại.

Ví dụ:

```
orders.created
orders.cancelled
payments.completed
users.registered
```

Một topic không chỉ chứa một message mà có thể chứa hàng triệu hoặc hàng tỷ message, phụ thuộc vào cách cấu hình và năng lực cluster.

### **2.3. Partition – phần quan trọng nhất**

Một topic được chia thành nhiều partition. Mỗi partition là một log lưu các record theo thứ tự.

Ví dụ topic `orders.created` có 3 partition:

**Topic: orders.created**

3 partitions

Partition 0

A · 0

B · 1

C · 2

Partition 1

D · 0

E · 1

F · 2

Partition 2

G · 0

H · 1

I · 2

Con số sau dấu chấm là offset. Mỗi partition có dãy offset riêng bắt đầu từ 0 trong minh họa.

**Tại sao cần chia partition?**

Vì Kafka muốn xử lý lượng dữ liệu lớn bằng cách chia công việc ra nhiều phần để các consumer có thể đọc song song.

Ví dụ:

- Partition 0: Consumer A xử lý.
- Partition 1: Consumer B xử lý.
- Partition 2: Consumer C xử lý.

Nhờ vậy, chúng ta có thể scale consumer để tăng throughput.

### **2.4. Message Key và Ordering**

Giả sử một đơn hàng có ba event:

```
OrderCreated
OrderPaid
OrderShipped
```

Bạn muốn xử lý đúng thứ tự:

```
Created → Paid → Shipped
```

Nếu ba event nằm ở những partition khác nhau thì Kafka không đảm bảo consumer sẽ xử lý chúng theo đúng thứ tự toàn cục.

Cách thường dùng là **chọn cùng message key**, ví dụ `OrderId = 1001`.

```
new Message<string, string>
{
    Key = orderId.ToString(),
    Value = json
}
```

Khi sử dụng cùng key và cùng cơ chế partitioning ổn định, các event của cùng order sẽ được đưa vào cùng partition.

Ví dụ: cùng key `order-1001`

Created

Paid

Shipped

Partition 1

Offset 10 → 11 → 12

Lưu ý:

- Kafka đảm bảo thứ tự record trong từng partition.
- Không đảm bảo thứ tự giữa các partition.
- Nếu consumer xử lý song song không kiểm soát hoặc có retry bất đồng bộ, ứng dụng vẫn có thể làm sai thứ tự xử lý.
- Tăng số lượng partition có thể thay đổi cách phân phối key đối với các event tương lai.

### **2.5. Offset là gì?**

Offset là vị trí của message bên trong partition.

Ví dụ:

```
Partition 0

Offset     Message
0          OrderCreated(1001)
1          OrderCreated(1002)
2          OrderCreated(1003)
3          OrderCreated(1004)
```

Consumer sử dụng offset để theo dõi tiến độ đọc message.

Nếu consumer đã xử lý xong offset 2 và commit thành công, thông thường committed offset sẽ là 3, nghĩa là vị trí tiếp theo cần đọc.

**Khác với một hàng đợi truyền thống:** Kafka không xóa ngay message khi consumer đọc xong. Message vẫn được giữ theo chính sách retention hoặc compaction của topic.

Vì vậy, consumer khác có thể đọc lại event, và một consumer cũng có thể replay event còn được lưu.

### **2.6. Consumer Group**

Đây là khái niệm rất hay gặp trong production.

Giả sử bạn có 3 consumer cùng group `email-service`.

Thử thay đổi số consumer

2 consumers

1

3

5

Topic: orders.created

Partition 0

Partition 1

Partition 2

Phân công partition minh họa

Consumer 1

P0, P2

Consumer 2

P1

Kafka phân chia 3 partition giữa các consumer đang hoạt động trong group.

Đây là mô phỏng đơn giản. Việc phân công thực tế phụ thuộc partition assignor và trạng thái consumer group.

Nếu có 3 partition nhưng 5 consumer trong cùng group thì với mô hình consumer group truyền thống, tối đa 3 consumer được phân công partition.

Đây là lý do số lượng partition có ảnh hưởng trực tiếp đến khả năng scale consumer.

**Một câu hỏi quan trọng:** Nếu Email Service và Inventory Service cùng đọc một event thì sao?

Chúng phải sử dụng **hai Consumer Group khác nhau**:

```
orders.created
     |
     +-- Group: email-service
     |      +-- Email Consumer 1
     |      +-- Email Consumer 2
     |
     +-- Group: inventory-service
            +-- Inventory Consumer 1
            +-- Inventory Consumer 2
```

Mỗi group có tiến độ đọc (committed offset) riêng. Vì vậy, cả Email Service và Inventory Service đều có thể nhận được mọi event phù hợp trong topic.

Ngược lại, các consumer cùng group chia nhau công việc, không phải mỗi consumer đều nhận toàn bộ event.

Kafka hiện đại còn có mô hình share group dành cho một số workload kiểu hàng đợi, nhưng trong hướng dẫn này chúng ta tập trung vào consumer group truyền thống vì đây là mô hình nền tảng cần hiểu khi xây dựng service .NET.&#x20;

## **Phần 3. Kafka Broker, Cluster và Replication**

LEVEL 2 · MIDDLE

Đây là phần giúp bạn hiểu tại sao Kafka có khả năng chịu lỗi.

Một Broker là một Kafka server. Một Kafka Cluster thường có nhiều broker.

Giả sử có ba broker và topic `orders.created` được cấu hình:

```
Partitions        = 3
ReplicationFactor = 3
```

Điều đó có nghĩa là mỗi partition có 3 bản sao đặt trên các broker khác nhau.

Kafka Cluster

Broker 1

P0 Leader

P1 Follower

P2 Follower

Broker 2

P0 Follower

P1 Leader

P2 Follower

Broker 3

P0 Follower

P1 Follower

P2 Leader

Leader

Follower

Mỗi partition có một leader. Producer thông thường gửi dữ liệu đến broker đang giữ leader của partition đó. Các follower sao chép dữ liệu từ leader.

Nếu broker chứa leader bị lỗi, Kafka có thể bầu một replica đủ điều kiện làm leader mới.

### **Replication Factor và&#x20;**`min.insync.replicas`

Trong production, hai cấu hình này cực kỳ quan trọng:

| Cấu hình              | Ví dụ | Ý nghĩa                                                                                |
| --------------------- | ----- | -------------------------------------------------------------------------------------- |
| `replication.factor`  | 3     | Mỗi partition có 3 replica                                                             |
| `min.insync.replicas` | 2     | Khi producer dùng `acks=all`, cần đủ số replica đồng bộ theo yêu cầu để ghi thành công |
| `acks`                | `all` | Producer chờ xác nhận theo cơ chế đồng bộ replica                                      |

Giả sử ba broker đang chạy, một broker bị lỗi:

- Nếu vẫn còn đủ replica trong ISR (in-sync replicas), producer tiếp tục ghi được.
- Nếu số lượng ISR giảm dưới `min.insync.replicas`, những request ghi với `acks=all` sẽ bị từ chối thay vì chấp nhận mức đảm bảo độ bền thấp hơn.

Cấu hình này đánh đổi một phần availability để bảo vệ durability.

**Production recommendation:** Với cluster tối thiểu 3 broker phục vụ workload quan trọng, `replication.factor=3`, `min.insync.replicas=2`, `acks=all` là một cấu hình xuất phát phổ biến. Tuy nhiên, còn phải xét topology, số availability zone, disk và nhu cầu chịu lỗi.

### **KRaft là gì?**

Kafka cần cơ chế quản lý metadata và điều phối cluster. Các phiên bản Kafka hiện đại sử dụng **KRaft** thay cho kiến trúc ZooKeeper cũ.

KRaft sử dụng controller quorum để quản lý metadata. Trong môi trường production, nên cân nhắc tách controller và broker theo quy mô và yêu cầu chịu lỗi, thay vì dùng một node kết hợp mọi vai trò như ví dụ local.

Tham khảo: [Apache Kafka Official Quickstart](https://kafka.apache.org/quickstart/?utm_source=chatgpt.com).

### **Bước 4. Tạo Producer**

Đầu tiên, tạo model event:

```
public sealed record OrderCreatedEvent(
    Guid EventId,
    int OrderId,
    int UserId,
    decimal TotalAmount,
    DateTime OccurredAt);
```

Tạo `appsettings.json`:

```
{
  "Kafka": {
    "BootstrapServers": "localhost:9092",
    "Topics": {
      "OrderCreated": "orders.created"
    }
  }
}
```

Tạo một producer đơn giản:

```

using Confluent.Kafka;
using System.Text.Json;

public sealed class KafkaProducer
{
    private readonly IProducer<string, string> _producer;

    public KafkaProducer(string bootstrapServers)
    {
        var config = new ProducerConfig
        {
            BootstrapServers = bootstrapServers,
            Acks = Acks.All,
            EnableIdempotence = true
        };

        _producer = new ProducerBuilder<string, string>(config)
            .Build();
    }

    public async Task PublishAsync<T>(
        string topic,
        string key,
        T data,
        CancellationToken cancellationToken = default)
    {
        var message = new Message<string, string>
        {
            Key = key,
            Value = JsonSerializer.Serialize(data)
        };

        await _producer.ProduceAsync(
            topic,
            message,
            cancellationToken);
    }
}

```

Trong code trên:

| Thành phần          | Ý nghĩa                                      |
| ------------------- | -------------------------------------------- |
| `BootstrapServers`  | Địa chỉ Kafka broker ban đầu                 |
| `Acks.All`          | Chờ xác nhận theo cấu hình replica           |
| `EnableIdempotence` | Giảm nguy cơ ghi trùng do retry của producer |
| `Key`               | Xác định cách event được phân vào partition  |
| `Value`             | Nội dung message                             |
| `ProduceAsync`      | Gửi message và chờ delivery result           |

Ví dụ gọi producer:

```
var orderEvent = new OrderCreatedEvent(
    Guid.NewGuid(),
    1001,
    25,
    500000,
    DateTime.UtcNow);

await kafkaProducer.PublishAsync(
    "orders.created",
    orderEvent.OrderId.ToString(),
    orderEvent,
    cancellationToken);
```

Khi `ProduceAsync` hoàn tất thành công, producer đã nhận delivery report thành công từ Kafka theo cấu hình acknowledgement. Điều đó **không có nghĩa consumer đã xử lý xong event**.

Trong production, nên đăng ký producer qua DI, tái sử dụng thread-safe `IProducer<TKey,TValue>` và dispose khi ứng dụng dừng, thay vì tạo một producer mới cho từng HTTP request.

### **Bước 5. Tạo Consumer bằng BackgroundService**

Chúng ta sẽ tạo một Worker đọc event và xử lý.

```

using Confluent.Kafka;
using System.Text.Json;

public sealed class OrderCreatedConsumer : BackgroundService
{
    private readonly ILogger<OrderCreatedConsumer> _logger;

    public OrderCreatedConsumer(
        ILogger<OrderCreatedConsumer> logger)
    {
        _logger = logger;
    }

    protected override Task ExecuteAsync(
        CancellationToken stoppingToken)
    {
        var config = new ConsumerConfig
        {
            BootstrapServers = "localhost:9092",
            GroupId = "order-notification-service",
            AutoOffsetReset = AutoOffsetReset.Earliest,
            EnableAutoCommit = false
        };

        using var consumer =
            new ConsumerBuilder<string, string>(config).Build();

        consumer.Subscribe("orders.created");

        try
        {
            while (!stoppingToken.IsCancellationRequested)
            {
                var result = consumer.Consume(stoppingToken);

                try
                {
                    var orderEvent =
                        JsonSerializer.Deserialize<OrderCreatedEvent>(
                            result.Message.Value);

                    if (orderEvent is null)
                    {
                        throw new InvalidDataException(
                            "Invalid order event");
                    }

                    _logger.LogInformation(
                        "Processing OrderId: {OrderId}",
                        orderEvent.OrderId);

                    // Handle business logic here.
                    // Only commit after processing succeeds.
                    consumer.Commit(result);
                }
                catch (Exception ex)
                {
                    _logger.LogError(
                        ex,
                        "Processing failed at {Offset}",
                        result.TopicPartitionOffset);

                    // Stop this consumer to avoid skipping
                    // a failed record by continuing to poll.
                    throw;
                }
            }
        }
        catch (OperationCanceledException)
            when (stoppingToken.IsCancellationRequested)
        {
            // Graceful shutdown.
        }
        finally
        {
            consumer.Close();
        }

        return Task.CompletedTask;
    }
}

```

Đăng ký Worker trong `Program.cs`:

```
builder.Services.AddHostedService<OrderCreatedConsumer>();
```

Đây là ví dụ học tập với xử lý đồng bộ đơn giản. Nếu consumer cần truy cập SQL Server, gửi email hoặc gọi API bất đồng bộ, nên chuyển sang vòng lặp async có kiểm soát thời gian xử lý, retry và shutdown. Không nên xem đoạn này là một Worker production hoàn chỉnh.

### **Bước 6. Hiểu rõ Commit Offset**

Giả sử consumer đang xử lý offset 10.

Vòng đời một message

1. **Consume offset 10**

   Nhận event từ Kafka
2. **Process event**

   Xử lý business logic, lưu dữ liệu
3. **Commit offset 11**

   Xác nhận vị trí tiếp theo cần đọc
4. **Consume offset 11**

   Tiếp tục xử lý event kế tiếp

Có hai tình huống cần đặc biệt chú ý:

**Trường hợp A: Commit trước khi xử lý**

```
Consume → Commit → Process → Crash
```

Nếu ứng dụng crash sau khi commit nhưng trước khi xử lý xong, message có thể bị bỏ qua sau khi restart.

**Trường hợp B: Xử lý trước khi commit**

```
Consume → Process → Crash → Commit chưa xảy ra
```

Message có thể được đọc lại, dẫn đến xử lý trùng.

Đó là lý do production thường dùng **At-least-once delivery kết hợp Idempotent Consumer**.

Trong Confluent.Kafka có hai chiến lược phổ biến:

| Chiến lược                | Cách dùng                                                                          | Đánh đổi                                  |
| ------------------------- | ---------------------------------------------------------------------------------- | ----------------------------------------- |
| Manual synchronous commit | `EnableAutoCommit=false` + `Commit()`                                              | Dễ hiểu nhưng có thể ảnh hưởng throughput |
| Manual offset store       | `EnableAutoCommit=true`, `EnableAutoOffsetStore=false` + `StoreOffset()` sau xử lý | Commit nền giúp throughput tốt hơn        |

Confluent khuyến nghị cân nhắc `StoreOffset` cho luồng xử lý at-least-once hiệu quả, nhưng cần quản lý rebalance và thứ tự hoàn thành xử lý.&#x20;

Confluent Documentation+1



Một điểm khác: `AutoOffsetReset.Earliest` không có nghĩa consumer luôn đọc lại từ đầu khi restart. Nó chỉ áp dụng khi group không có committed offset hợp lệ hoặc offset không còn tồn tại theo tình huống cấu hình reset.

# **Phần 6. Những bài toán Kafka thường gặp trong Production**

LEVEL 3 · SENIOR

Đây là phần quan trọng nhất nếu mục tiêu của bạn là tự thiết kế hệ thống thay vì chỉ biết gửi và nhận message.

## **6.1. At-most-once, At-least-once và Exactly-once**

Đây là ba khái niệm về delivery semantics.

| Cơ chế        | Ý nghĩa                                                                | Rủi ro                                                       |
| ------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------ |
| At-most-once  | Message có thể được xử lý 0 hoặc 1 lần                                 | Có thể mất xử lý                                             |
| At-least-once | Message được xử lý ít nhất một lần trong các điều kiện đảm bảo phù hợp | Có thể xử lý trùng                                           |
| Exactly-once  | Hiệu ứng xử lý xảy ra đúng một lần trong phạm vi đảm bảo xác định      | Phức tạp hơn, không tự động áp dụng cho hệ thống ngoài Kafka |

Kafka hỗ trợ idempotent producer và transaction để xây dựng exactly-once processing cho những pipeline Kafka-to-Kafka phù hợp.

Nhưng ví dụ bạn consume một event để trừ tiền trong SQL Server, Kafka transaction **không tự động biến thao tác cập nhật SQL thành exactly-once**.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://kafka.apache.org\&sz=32)

Apache Kafka+1



Vì vậy, với .NET và SQL Server, chiến lược thực tế thường là:

**At-least-once + Idempotent Consumer.**

## **6.2. Idempotent Consumer – xử lý message trùng**

Giả sử Kafka gửi event:

```
{
  "eventId": "a7c4f2",
  "orderId": 1001,
  "amount": 500000
}
```

Consumer nhận event và cập nhật SQL Server thành công.

Ngay sau đó ứng dụng crash, trước khi commit offset.

Khi chạy lại, Kafka có thể giao lại event đó.

Nếu code chỉ đơn giản như sau:

```
order.TotalPaid += message.Amount;
```

Thì số tiền sẽ bị cộng hai lần.

### **Giải pháp: Lưu EventId đã xử lý**

Tạo bảng SQL Server:

```
CREATE TABLE ProcessedMessages
(
    ConsumerName NVARCHAR(100) NOT NULL,
    EventId UNIQUEIDENTIFIER NOT NULL,
    ProcessedAt DATETIME2 NOT NULL
        DEFAULT SYSUTCDATETIME(),

    CONSTRAINT PK_ProcessedMessages
        PRIMARY KEY (ConsumerName, EventId)
);
```

Luồng xử lý:

**Consume Event**

**BEGIN SQL TRANSACTION**

**Insert EventId vào ProcessedMessages**

Insert thành công

Update business data

COMMIT SQL

EventId đã tồn tại

Duplicate Event

Skip business logic

**Commit Kafka Offset**

Điểm cần nhớ:

- Việc insert `ProcessedMessages` và cập nhật business data phải nằm trong **cùng một SQL transaction**.
- Unique constraint là cơ chế chống race condition khi nhiều worker cùng gặp một event.
- Chỉ coi duplicate key của chính constraint idempotency là event đã xử lý; lỗi SQL khác phải được xử lý bình thường.
- Commit Kafka offset sau khi SQL transaction đã commit.
- Nếu xử lý business hoặc ghi marker thất bại, rollback cả hai.
- Đối với external API như gửi email, cần thêm idempotency key, deduplication hoặc cơ chế riêng ở hệ thống nhận.

Đây là giải pháp giúp chống xử lý trùng ở tầng application, không phải phép bảo đảm tuyệt đối rằng mọi side effect bên ngoài đều xảy ra một lần.

## **6.3. Transactional Outbox Pattern – tránh mất event**

Đây là một trong những pattern quan trọng nhất khi dùng Kafka với database.

Giả sử bạn có code:

```
await dbContext.Orders.AddAsync(order);
await dbContext.SaveChangesAsync();

await kafkaProducer.PublishAsync(
    "orders.created",
    order.Id.ToString(),
    orderCreatedEvent);
```

Thoạt nhìn code khá hợp lý.

Nhưng nếu `SaveChangesAsync()` thành công, sau đó Kafka bị lỗi thì sao?

Kết quả:

```
SQL Server: Order đã được lưu
Kafka: Không có OrderCreated event
Email Service: Không biết có đơn hàng mới
```

Đây là vấn đề **Dual Write**.

### **Giải pháp: Transactional Outbox**

**Order API**

SQL Transaction

Orders

INSERT Order

OutboxMessages

INSERT Event

COMMIT cùng transaction

**Outbox Publisher (BackgroundService)**

Đọc event chưa gửi và publish

**Kafka: orders.created**

**Consumer Service**

Quy trình:

1. API tạo Order.
2. API tạo OutboxMessage.
3. Cả hai record được lưu trong cùng một SQL transaction.
4. BackgroundService đọc các outbox message chưa publish.
5. Worker gửi event lên Kafka.
6. Nếu Kafka xác nhận thành công, Worker đánh dấu event đã publish.

Nếu Kafka bị lỗi, outbox message vẫn nằm trong database và có thể được retry.

Nếu Worker đã publish thành công nhưng crash trước khi đánh dấu đã gửi thì event có thể được publish lại. Vì vậy phía Consumer vẫn cần idempotency.

Một bảng Outbox đơn giản:

```
CREATE TABLE OutboxMessages
(
    Id UNIQUEIDENTIFIER PRIMARY KEY,
    EventType NVARCHAR(200) NOT NULL,
    Payload NVARCHAR(MAX) NOT NULL,
    CreatedAt DATETIME2 NOT NULL,
    PublishedAt DATETIME2 NULL,
    RetryCount INT NOT NULL DEFAULT 0
);
```

**Những vấn đề senior cần giải quyết thêm:**

- Nhiều Outbox Worker chạy song song có đọc trùng không?
- Làm sao claim event an toàn bằng lock/lease?
- Worker crash giữa lúc publish và update status thì sao?
- Làm sao ngăn event cũ chặn toàn bộ hàng đợi?
- Khi retry, làm sao không phá ordering theo aggregate?
- Outbox table tăng đến hàng chục triệu record thì cleanup và index thế nào?

Nếu bạn đã quen với `UPDLOCK`, `READPAST`, transaction và concurrency trong SQL Server thì đây là một bài toán rất phù hợp để thực hành.

## **6.4. Retry và Dead Letter Topic**

Một trường hợp thực tế khác: Consumer nhận message nhưng xử lý thất bại.

Ví dụ Email Service gọi SMTP và SMTP server bị timeout.

Bạn cần phân loại lỗi trước khi quyết định retry.

| Loại lỗi          | Ví dụ                                  | Cách xử lý                              |
| ----------------- | -------------------------------------- | --------------------------------------- |
| Transient         | Network timeout, HTTP 503              | Retry có giới hạn                       |
| Permanent         | Email format không hợp lệ              | Không retry vô hạn                      |
| Poison message    | JSON lỗi hoặc schema không tương thích | Quarantine/DLT, cảnh báo                |
| Business conflict | Trạng thái đơn hàng không hợp lệ       | Tùy business, điều tra hoặc xử lý riêng |

Một thiết kế có thể dùng:

```
orders.created
       |
       v
   Email Consumer
       |
       +-- Success --> Commit Offset
       |
       +-- Failed
               |
               v
          Retry Policy
               |
               +-- Success --> Commit
               |
               +-- Exhausted
                       |
                       v
              orders.created.dlt
```

Ví dụ với .NET có thể sử dụng Polly để retry các transient errors trong phạm vi consumer.

Nhưng có một điểm cần chú ý: **Kafka không có cơ chế per-message nack/requeue giống RabbitMQ classic queue**.

Khi sử dụng retry topic hoặc DLT, ứng dụng phải quản lý việc publish, commit và chuyển trạng thái phù hợp.

Một nguyên tắc quan trọng: Nếu bạn publish message lỗi sang DLT, chỉ commit offset của nguồn sau khi đã nhận được xác nhận DLT publish thành công và chấp nhận semantics của luồng chuyển tiếp đó.

Với yêu cầu cao hơn, cần tính đến Kafka transaction cho luồng Kafka-to-Kafka hoặc cơ chế phục hồi tương đương.

### **Retry có thể phá ordering**

Ví dụ các event của cùng Order:

```
OrderCreated
OrderPaid
OrderShipped
```

Nếu `OrderCreated` bị lỗi và chuyển sang retry topic, còn consumer chính tiếp tục xử lý `OrderPaid`, thứ tự business có thể bị sai.

Vì vậy, khi cần strict ordering theo OrderId, bạn phải chọn chiến lược retry phù hợp, chẳng hạn chặn tiến độ partition có kiểm soát hoặc sử dụng state/version để bảo vệ business invariant.

Không nên áp dụng retry topic một cách máy móc cho mọi event.

## **Phần 7. Best Practices Kafka cho Production**

### **7.1. Producer configuration**

Ví dụ cấu hình khởi đầu cho workload cần độ tin cậy cao:

```
var config = new ProducerConfig
{
    BootstrapServers = "kafka1:9092,kafka2:9092,kafka3:9092",

    Acks = Acks.All,
    EnableIdempotence = true,

    MessageTimeoutMs = 30000,
    LingerMs = 5
};
```

Đây là baseline tham khảo, không phải giá trị tối ưu cho mọi hệ thống.

| Property            | Best practice                                      |
| ------------------- | -------------------------------------------------- |
| `Acks`              | Dùng `All` cho event quan trọng                    |
| `EnableIdempotence` | Bật để hỗ trợ retry an toàn của producer           |
| `LingerMs`          | Điều chỉnh batching để cân bằng latency/throughput |
| `MessageTimeoutMs`  | Đặt giới hạn phù hợp với SLA                       |
| `CompressionType`   | Cân nhắc Snappy, LZ4 hoặc Zstd cho lưu lượng lớn   |
| `BootstrapServers`  | Cấu hình nhiều broker khả dụng                     |
| `SecurityProtocol`  | Dùng TLS/SASL theo môi trường                      |

Lưu ý `EnableIdempotence=true` không chống được mọi trường hợp duplicate ở tầng business. Nếu application tự publish lại cùng một event sau khi restart, broker vẫn có thể nhận một record mới.

### **7.2. Consumer configuration**

```
var config = new ConsumerConfig
{
    BootstrapServers = "kafka1:9092,kafka2:9092,kafka3:9092",

    GroupId = "email-service",

    AutoOffsetReset = AutoOffsetReset.Earliest,

    EnableAutoCommit = true,
    EnableAutoOffsetStore = false,

    AutoCommitIntervalMs = 5000,
    MaxPollIntervalMs = 300000
};
```

Với cấu hình này:

- Consumer đọc message.
- Thực hiện business logic.
- Sau khi xử lý xong, gọi `StoreOffset(result)`.
- Client commit offset đã được store theo chu kỳ nền.

Nếu Worker crash trước khi offset được commit thì message có thể được xử lý lại.

Cần xử lý graceful shutdown, rebalance và không store offset vượt quá những message chưa xử lý trong cùng partition.&#x20;

| Property              | Khởi điểm tham khảo | Ghi chú                                                                  |
| --------------------- | ------------------- | ------------------------------------------------------------------------ |
| Partitions            | 3–12                | Không có con số tối ưu chung; phụ thuộc throughput, ordering và consumer |
| Replication factor    | 3                   | Khi cluster có đủ broker                                                 |

## **Phần 8. Monitoring và vận hành Kafka**

LEVEL 3 · PRODUCTION OPERATIONS

Một senior developer cần biết không chỉ cách publish/consume mà còn cách xác định hệ thống có đang xử lý tốt hay không.

### **Consumer Lag là gì?**

Consumer lag biểu thị mức chênh lệch giữa vị trí cuối của log trên partition và committed offset của consumer group.

Ví dụ:

Log end offset

# **10,000**

Committed offset

# **8,500**

85% vị trí log đã tiến tới

Lag 1,500 records

Ví dụ minh họa một partition. Lag là số record chưa được commit, không trực tiếp tương đương thời gian trễ xử lý.

Nếu Producer gửi 1.000 message/giây nhưng Consumer chỉ xử lý 600 message/giây thì backlog sẽ tăng.

Consumer lag tăng liên tục có thể do:

- Consumer xử lý quá chậm.
- Downstream database/API bị nghẽn.
- Số lượng consumer hoặc partition chưa phù hợp.
- Một partition có traffic cao hơn những partition còn lại.
- Retry kéo dài hoặc poison message.
- Consumer rebalance liên tục.

### **Các metric nên theo dõi**

- **Consumer lag:** Số record consumer chưa bắt kịp.
- **Processing latency:** Thời gian xử lý một event.
- **Throughput:** Số message/giây.
- **Error/retry/DLT rate:** Tỷ lệ lỗi, retry và message vào dead-letter topic.
- **Rebalance frequency:** Tần suất Kafka phải phân chia lại partition.
- **Broker health:** Disk, memory, network, under-replicated partitions, offline partitions và trạng thái ISR.
- **Outbox backlog:** Số event đã lưu trong DB nhưng chưa publish.

Trong thực tế, bạn có thể sử dụng Prometheus, Grafana và OpenTelemetry kết hợp metrics exporter phù hợp.

Khi log, nên thêm `EventId`, `CorrelationId`, `Topic`, `Partition`, `Offset` và business identifier như `OrderId`.

Đặc biệt, không nên chỉ dựa vào consumer lag. Nếu application commit offset sai thời điểm, lag có thể bằng 0 trong khi business logic chưa xử lý thành công.

## **Phần 9. Kafka so với RabbitMQ và AWS SQS**

Vì .NET Developer thường sử dụng cả RabbitMQ, SQS và Kafka, nên việc chọn đúng công nghệ quan trọng hơn việc cố sử dụng Kafka cho mọi tính năng.

| Tiêu chí              | Kafka                                 | RabbitMQ                                  | AWS SQS                                             |
| --------------------- | ------------------------------------- | ----------------------------------------- | --------------------------------------------------- |
| Mục tiêu nổi bật      | Event streaming, durable log          | Message broker, task routing              | Managed message queue                               |
| Replay event          | Điểm mạnh cốt lõi                     | Tùy cơ chế và loại queue/stream           | Giới hạn theo retention, không phải event log tùy ý |
| Nhiều service độc lập | Consumer groups                       | Exchange và nhiều queue                   | Kết hợp SNS/EventBridge hoặc nhiều queue            |
| Ordering              | Trong partition                       | Phụ thuộc queue, consumer và cơ chế xử lý | FIFO có ordering theo message group                 |
| Retention sau xử lý   | Theo retention/compaction             | Khác nhau giữa queue và stream            | Message đã xóa không còn trong queue                |
| Vận hành              | Phức tạp hơn nếu self-host            | Thường đơn giản hơn với task queue nhỏ    | AWS quản lý hạ tầng                                 |
| Trường hợp nổi bật    | Event-driven platform, CDC, analytics | Background jobs, routing, workflows       | AWS async jobs, decoupling                          |

## **Phần 10. Những vấn đề nâng cao ở cấp Senior**

Có một số vấn đề khi làm Kafka production mà chỉ biết Producer/Consumer là chưa đủ.

### **10.1. Rebalance**

Giả sử Consumer A đang xử lý Partition 0.

Khi một consumer mới tham gia group hoặc consumer hiện tại ngừng hoạt động, Kafka có thể thực hiện rebalance để phân công lại partition.

Nếu A đang xử lý một event lâu, sau đó mất quyền sở hữu partition, commit có thể thất bại. Consumer mới có thể đọc lại event đó.

Đây là một lý do khác khiến idempotency cực kỳ quan trọng.

Với task xử lý lâu, cần thiết kế cách poll, giới hạn thời gian xử lý, partition pause/resume, graceful shutdown và bảo đảm không commit vượt tiến độ xử lý.

### **10.2. Hot Partition**

Ví dụ topic có 10 partition nhưng một khách hàng lớn tạo ra 80% traffic.

Nếu sử dụng `CustomerId` làm key, toàn bộ event của khách hàng đó có thể vào cùng một partition.

Kết quả:

- Một consumer bị quá tải.
- Những consumer khác còn rảnh.
- Consumer lag của partition đó tăng cao.

Cần cân bằng giữa ordering theo key và khả năng phân phối tải. Không phải lúc nào tăng số consumer cũng giải quyết được hot partition.

### **10.3. Event Schema Evolution**

Ban đầu `OrderCreated` có:

```
{
  "orderId": 1001,
  "amount": 500000
}
```

Sau này bạn thêm:

```
{
  "orderId": 1001,
  "amount": 500000,
  "currency": "VND"
}
```

Nếu thay đổi không tương thích, consumer cũ có thể lỗi.

Trong production, nên có version strategy và quản lý schema compatibility. Có thể sử dụng JSON Schema, Avro hoặc Protobuf cùng Schema Registry tùy ecosystem.

Nguyên tắc là không được giả định mọi producer và consumer đều deploy cùng một thời điểm.

### **10.4. Backpressure**

Producer có thể publish nhanh hơn khả năng xử lý của consumer.

Không nên tạo vô hạn `Task.Run` để xử lý song song vì có thể gây cạn tài nguyên, tăng độ trễ và làm phức tạp offset management.

Với .NET, `System.Threading.Channels` có thể hỗ trợ bounded buffering, nhưng cần quản lý tiến độ hoàn thành theo từng partition. Consumer không được store/commit offset mới hơn trong khi message trước đó của cùng partition vẫn chưa xử lý thành công.

## **Tổng kết – Tư duy của một Senior .NET Developer khi sử dụng Kafka**

Khi thiết kế một tính năng dùng Kafka, bạn nên trả lời được các câu hỏi sau:

1. **Tại sao chọn Kafka?** Có thật sự cần event streaming, replay hoặc nhiều consumer độc lập không?
2. **Message key là gì?** Business entity nào cần được bảo đảm thứ tự?
3. **Nếu publish thất bại thì sao?** Có cần Transactional Outbox không?
4. **Nếu consumer xử lý trùng thì sao?** Đã có idempotency chưa?
5. **Nếu consumer bị lỗi liên tục thì sao?** Retry, DLT và recovery hoạt động thế nào?
6. **Nếu lưu lượng tăng gấp 10 lần thì sao?** Partition, consumer group và backpressure được thiết kế như thế nào?
7. **Làm sao biết hệ thống đang chạy tốt?** Có metrics, logs, tracing, alert và phương án phục hồi chưa?

Nếu bạn mới bắt đầu, hãy tập trung thật chắc vào **Topic → Partition → Consumer Group → Offset → Commit** trước. Sau đó hãy xây dựng một project .NET có Producer và Worker, rồi chủ động tạo tình huống crash để kiểm tra behavior.

Khi đã xử lý được bài toán **SQL Server + Kafka + Outbox + Idempotent Consumer**, bạn sẽ hiểu được phần lớn các vấn đề reliability quan trọng mà Kafka mang lại trong kiến trúc event-driven production.
