# **Unit Testing trong .NET — Từ tư duy Developer đến Best Practices trong Production**

Tài liệu học tập dành cho .NET Developer • Beginner → Senior • ASP.NET Core, C#, xUnit, Moq

**Mục tiêu:** Không chỉ biết cách viết Unit Test bằng xUnit hay Moq, mà còn hiểu tại sao phải test, nên test những gì, test đến đâu là đủ, và cách tổ chức Unit Test trong một dự án thực tế.

## **1. Tư duy của Developer chuyển sang Testing**

### **1.1. Sự khác nhau giữa tư duy Coding và Testing**

Khi phát triển một chức năng, Developer thường tập trung vào câu hỏi:

> Làm thế nào để chức năng này hoạt động đúng theo requirement?

Khi viết Unit Test, chúng ta cần thay đổi cách suy nghĩ:

> Trong những trường hợp nào chức năng này có thể hoạt động sai? Và làm thế nào để chứng minh nó vẫn hoạt động đúng?

Ví dụ, bạn cần phát triển API chuyển tiền giữa hai tài khoản.

**Tư duy của Developer:**

1. Kiểm tra tài khoản nguồn.
2. Kiểm tra số dư.
3. Trừ tiền tài khoản nguồn.
4. Cộng tiền tài khoản đích.
5. Lưu database.
6. Trả về thành công.

**Tư duy của Tester:**

- Chuyển 100.000đ khi tài khoản có 500.000đ?
- Chuyển 100.000đ khi tài khoản chỉ có 50.000đ?
- Chuyển số tiền bằng 0 hoặc âm?
- Tài khoản nguồn không tồn tại?
- Hai tài khoản trùng nhau?
- Hai yêu cầu chuyển tiền đến cùng lúc?
- Database lỗi sau khi trừ tiền nhưng chưa cộng tiền?
- Người dùng gửi lại cùng một request chuyển tiền?

Điểm khác biệt quan trọng là Developer thường bắt đầu bằng **happy path**, còn khi thiết kế test, chúng ta phải nghĩ đến cả **negative path, boundary case và failure scenario**.

### **1.2. Năm nhóm test case Developer nên suy nghĩ**

| Nhóm           | Mục tiêu                  | Ví dụ                            |
| -------------- | ------------------------- | -------------------------------- |
| Happy Path     | Luồng thành công          | Chuyển tiền hợp lệ               |
| Negative Path  | Đầu vào không hợp lệ      | Số tiền âm                       |
| Boundary Case  | Giá trị ở ranh giới       | Số dư bằng số tiền chuyển        |
| Exception Case | Hệ thống gặp lỗi          | Repository ném exception         |
| Business Rule  | Đảm bảo quy tắc nghiệp vụ | Không chuyển tiền cho chính mình |

Không phải trường hợp nào cũng phù hợp với Unit Test. Ví dụ, kiểm tra database transaction hoặc hai request cập nhật dữ liệu đồng thời thường cần Integration Test.

### **1.3. Một kỹ thuật tư duy thực tế**

Trước khi implement một method, hãy tự trả lời ba câu hỏi:

- **Input:** Method nhận dữ liệu gì? Giá trị nào hợp lệ và không hợp lệ?
- **Behavior:** Với từng input, hệ thống phải xử lý thế nào?
- **Output/Side Effect:** Method trả về gì, thay đổi trạng thái gì, hoặc gọi đến dependency nào?

Đây là nền tảng để chuyển từ tư duy viết code sang tư duy kiểm chứng hành vi.

## **2. Tại sao cần Unit Test?**

Unit Test là phương pháp kiểm thử một đơn vị hành vi nhỏ của phần mềm trong môi trường được kiểm soát.

Trong ASP.NET Core, đơn vị được test có thể là một method, một service hoặc một nhóm class nhỏ cùng thực hiện một hành vi nghiệp vụ.

### **2.1. Phát hiện bug sớm**

Ví dụ bạn có chức năng tính chiết khấu:

```
public decimal CalculateDiscount(
    decimal price,
    decimal discountPercent)
{
    return price - (price * discountPercent / 100);
}
```

Giả sử requirement quy định discount chỉ được từ 0% đến 100%.

Code trên vẫn chấp nhận `discountPercent = 150`, dẫn đến giá âm.

Unit Test giúp kiểm tra các trường hợp này trước khi code được deploy.

### **2.2. Giảm regression bug**

Regression bug là lỗi xuất hiện khi bạn sửa hoặc thêm một chức năng nhưng vô tình làm hỏng chức năng đã chạy đúng trước đó.

Ví dụ:

- Version 1: Người dùng được giảm 10%.
- Version 2: Thêm chương trình giảm giá VIP.
- Developer sửa `CalculateDiscount`.
- Logic giảm giá dành cho khách hàng thường bị sai.

Nếu các business rule cũ có Unit Test, chúng có thể phát hiện lỗi ngay khi bạn chạy test hoặc CI pipeline.

### **2.3. Tăng sự tự tin khi refactor**

Đây là lợi ích đặc biệt quan trọng trong production.

Giả sử bạn cần refactor một `OrderService` dài 1.000 dòng thành nhiều service nhỏ hơn.

Nếu không có test, bạn phải kiểm tra lại rất nhiều chức năng bằng tay.

Nếu có bộ test chất lượng, bạn có thể thay đổi implementation và nhanh chóng kiểm chứng rằng những behavior quan trọng vẫn được giữ nguyên.

Lưu ý: Unit Test không đảm bảo hệ thống hoàn toàn không có bug.

### **2.4. Unit Test như một dạng tài liệu**

Tên test có thể mô tả rõ business rule:

```
[Fact]
public void Withdraw_ShouldThrow_WhenBalanceIsInsufficient()
```

Người mới vào dự án nhìn test có thể hiểu:

> Khi số dư không đủ, hệ thống phải từ chối rút tiền.

Đây là một dạng tài liệu có thể thực thi (*executable documentation*).

### **2.5. Hỗ trợ CI/CD**

**Developer push code**

Git repository

**CI Pipeline**

Build + Run Unit Tests

**Tests Pass**

Cho phép tiếp tục các bước kiểm tra và release

**Tests Fail**

Chặn pipeline, yêu cầu sửa lỗi

Trong production, một bộ Unit Test nhanh và ổn định giúp team nhận feedback liên tục mỗi khi có code mới.

## **3. Nhược điểm của Unit Test**

Mặc dù quan trọng, Unit Test không phải giải pháp cho mọi vấn đề.

### **3.1. Không kiểm tra toàn bộ hệ thống**

Ví dụ:

```
public async Task<User?> GetUserAsync(int id)
{
    return await _repository.GetByIdAsync(id);
}
```

Bạn mock repository để trả về một `User` và Unit Test thành công.

Nhưng khi deploy, API vẫn có thể lỗi do:

- Connection string sai.
- SQL query không hợp lệ.
- EF Core mapping sai.
- Database thiếu migration.
- Dependency Injection cấu hình sai.

Bởi vì Unit Test đã thay thế repository thực, nên nó không kiểm tra được những vấn đề này.

### **3.2. Mock có thể khiến test thành công giả**

Ví dụ:

```
repositoryMock
    .Setup(x => x.GetByIdAsync(1))
    .ReturnsAsync(new User { Id = 1 });
```

Test này chỉ xác nhận service xử lý đúng với dữ liệu mà mock cung cấp.

Nó không chứng minh repository thật có thể lấy user từ database.

**Unit Test pass không đồng nghĩa toàn bộ feature đã hoạt động đúng trong production.**

### **3.3. Tăng chi phí bảo trì**

Khi business rule thay đổi, test cũng cần thay đổi.

Đặc biệt, nếu test phụ thuộc quá nhiều vào chi tiết implementation, việc refactor một method có thể khiến hàng chục test thất bại dù behavior thực tế không thay đổi.

### **3.4. Có thể tạo cảm giác an toàn giả**

Một dự án đạt 95% Code Coverage nhưng vẫn có bug nghiêm trọng.

Ví dụ, test có chạy qua đoạn code xử lý thanh toán, nhưng không assert số tiền cuối cùng.

Coverage cao không chứng minh logic đã được kiểm chứng đầy đủ.

### **3.5. Không phải logic nào cũng đáng viết Unit Test**

Ví dụ:

```
public string GetName() => Name;
```

Một method chỉ trả về property, không có business rule, thường không đem lại nhiều giá trị nếu phải viết test riêng.

Thay vào đó, nên ưu tiên:

- Business logic phức tạp.
- Permission, authentication và authorization rules.
- Tính toán tài chính.
- Validation nghiệp vụ.
- State transition.
- Các bug từng xảy ra trong production.

## **4. Đặc tính của một Unit Test tốt**

Một nguyên tắc phổ biến là **FIRST**.

## **F**

**Fast**

Chạy nhanh

## **I**

**Independent / Isolated**

Độc lập, cô lập

## **R**

**Repeatable**

Có thể chạy lặp lại

## **S**

**Self-validating**

Tự xác định Pass/Fail

## **T**

**Timely**

Viết đúng thời điểm

### **4.1. Fast — Chạy nhanh**

Unit Test lý tưởng thường chạy trong vài mili-giây hoặc thời gian ngắn.

Tránh gọi trực tiếp:

- Database thật.
- External API.
- RabbitMQ server.
- Redis server.
- File system nếu không cần thiết.

Những dependency này khiến test chậm, phụ thuộc môi trường và dễ phát sinh lỗi không liên quan.

### **4.2. Independent — Độc lập**

Test A không được phụ thuộc vào kết quả của Test B.

Ví dụ không tốt:

```
private static decimal _balance = 1000;

[Fact]
public void TestA()
{
    _balance -= 500;
}

[Fact]
public void TestB()
{
    Assert.Equal(500, _balance);
}
```

`TestB` phụ thuộc vào việc `TestA` chạy trước.

Trong xUnit, thứ tự chạy test không nên được giả định.

Cách tốt hơn là tạo dữ liệu mới cho từng test.

### **4.3. Repeatable — Chạy bao nhiêu lần cũng giống nhau**

Một Unit Test tốt phải cho kết quả nhất quán khi input và code không thay đổi.

Ví dụ không tốt:

```
[Fact]
public void TestExpired()
{
    var expired = DateTime.UtcNow.Day == 31;
    Assert.False(expired);
}
```

Kết quả phụ thuộc thời gian thực.

Trong production, nên inject `TimeProvider` hoặc một abstraction để kiểm soát thời gian.

### **4.4. Self-validating — Tự xác định kết quả**

Test phải có assertion rõ ràng.

Không tốt:

```
[Fact]
public void TestCalculate()
{
    var result = calculator.Add(2, 3);
    Console.WriteLine(result);
}
```

Test này có thể pass ngay cả khi kết quả bị sai.

Tốt hơn:

```
[Fact]
public void Add_ShouldReturnFive_WhenInputsAreTwoAndThree()
{
    var result = calculator.Add(2, 3);

    Assert.Equal(5, result);
}
```

### **4.5. Timely — Viết test đúng thời điểm**

Có hai cách thường gặp:

**Test After Development:** Implement chức năng trước, sau đó viết test để xác minh.

**Test-Driven Development (TDD):** Viết test trước, sau đó implement code để test pass, cuối cùng refactor.

Không nhất thiết phải áp dụng TDD cho toàn bộ dự án. Nhưng test nên được viết gần thời điểm phát triển feature, thay vì để đến cuối dự án mới bổ sung.

## **5. Fake, Stub và Mock trong Unit Test**

Đây là phần rất quan trọng vì Developer thường nhầm lẫn các khái niệm này.

Trước hết cần hiểu **Test Double**.

Test Double là một đối tượng được sử dụng thay thế dependency thật trong quá trình test.

Ví dụ:

```
public class UserService
{
    private readonly IUserRepository _repository;

    public UserService(IUserRepository repository)
    {
        _repository = repository;
    }
}
```

Khi chạy production, service sử dụng repository thật để thao tác database.

Khi Unit Test, chúng ta có thể thay repository thật bằng Fake, Stub hoặc Mock.

### **5.1. Stub — Cung cấp dữ liệu giả cố định**

Stub chủ yếu dùng để trả về dữ liệu mà test mong muốn.

Ví dụ:

```
public class StubUserRepository : IUserRepository
{
    public Task<User?> GetByIdAsync(int id)
    {
        return Task.FromResult<User?>(
            new User
            {
                Id = 1,
                Name = "John"
            });
    }
}
```

Khi test `UserService`, bạn không cần database.

```
var repository = new StubUserRepository();
var service = new UserService(repository);
```

**Mục đích:** Kiểm soát input từ dependency, từ đó kiểm tra kết quả của service.

### **5.2. Fake — Implementation đơn giản thay cho hệ thống thật**

Fake là implementation hoạt động được, nhưng được đơn giản hóa để phục vụ test.

Ví dụ, thay vì SQL Server, bạn tạo repository lưu dữ liệu bằng `Dictionary`.

```
public class FakeUserRepository : IUserRepository
{
    private readonly Dictionary<int, User> _users = new();

    public Task<User?> GetByIdAsync(int id)
    {
        _users.TryGetValue(id, out var user);
        return Task.FromResult(user);
    }

    public void Add(User user)
    {
        _users[user.Id] = user;
    }
}
```

Khác với Stub, Fake có thể quản lý trạng thái và thực hiện nhiều thao tác.

Tuy nhiên, Fake bằng `Dictionary` không mô phỏng chính xác transaction, constraint hoặc query semantics của SQL Server.

### **5.3. Mock — Kiểm tra cách đối tượng tương tác với dependency**

Mock thường được dùng khi bạn quan tâm một dependency có được gọi đúng hay không.

Ví dụ, khi đăng ký user thành công, hệ thống phải gửi một email chào mừng.

```
var emailMock = new Mock<IEmailService>();

await userService.RegisterAsync(request);

emailMock.Verify(
    x => x.SendWelcomeEmailAsync(
        request.Email),
    Times.Once);
```

Test xác nhận `SendWelcomeEmailAsync` được gọi đúng một lần.

Đặc biệt hữu ích khi kiểm tra side effect như gửi email, publish event hoặc ghi audit.

### **5.4. So sánh Fake, Stub, Mock**

|                      | Stub                    | Fake                           | Mock                   |
| -------------------- | ----------------------- | ------------------------------ | ---------------------- |
| Mục đích             | Trả dữ liệu             | Thay implementation thật       | Kiểm tra tương tác     |
| Có trạng thái?       | Thường không            | Thường có                      | Có thể                 |
| Kiểm tra số lần gọi? | Không phải mục tiêu     | Không phải mục tiêu            | Có                     |
| Ví dụ                | Trả User cố định        | Repository in-memory           | Verify gửi email       |
| Khi dùng             | Cần input từ dependency | Cần mô phỏng behavior đơn giản | Cần verify side effect |

Một điểm dễ nhầm: Trong thư viện **Moq**, `Mock<T>` không chỉ dùng để mock theo nghĩa hẹp. Nó cũng có thể cấu hình `ReturnsAsync(...)` để đóng vai trò Stub.

Vì vậy, tên thư viện và khái niệm Test Double không hoàn toàn trùng nhau.

## **6. Ví dụ Unit Test thực tế với ASP.NET Core, xUnit và Moq**

Giả sử bạn có requirement:

> Khi người dùng đăng ký tài khoản, hệ thống phải kiểm tra email đã tồn tại hay chưa. Nếu tồn tại thì từ chối. Nếu chưa tồn tại thì lưu user và gửi email chào mừng.

### **6.1. Production code**

```
public record RegisterRequest(string Email);

public interface IUserRepository
{
    Task<bool> ExistsByEmailAsync(string email);
    Task AddAsync(User user);
}

public interface IEmailService
{
    Task SendWelcomeEmailAsync(string email);
}

public class UserService
{
    private readonly IUserRepository _repository;
    private readonly IEmailService _emailService;

    public UserService(
        IUserRepository repository,
        IEmailService emailService)
    {
        _repository = repository;
        _emailService = emailService;
    }

    public async Task RegisterAsync(RegisterRequest request)
    {
        if (await _repository.ExistsByEmailAsync(request.Email))
        {
            throw new InvalidOperationException(
                "Email already exists");
        }

        var user = new User
        {
            Email = request.Email
        };

        await _repository.AddAsync(user);
        await _emailService.SendWelcomeEmailAsync(request.Email);
    }
}
```

Ví dụ được giản lược để tập trung vào Unit Test; production cần xử lý thêm các vấn đề như unique constraint, commit transaction và độ tin cậy khi gửi email.

### **6.2. Test case 1 — Email đã tồn tại**

```
[Fact]
public async Task RegisterAsync_ShouldThrow_WhenEmailAlreadyExists()
{
    // Arrange
    var repositoryMock = new Mock<IUserRepository>();
    var emailMock = new Mock<IEmailService>();

    repositoryMock
        .Setup(x => x.ExistsByEmailAsync("john@gmail.com"))
        .ReturnsAsync(true);

    var service = new UserService(
        repositoryMock.Object,
        emailMock.Object);

    // Act
    var action = () => service.RegisterAsync(
        new RegisterRequest("john@gmail.com"));

    // Assert
    await Assert.ThrowsAsync<InvalidOperationException>(action);

    repositoryMock.Verify(
        x => x.AddAsync(It.IsAny<User>()),
        Times.Never);

    emailMock.Verify(
        x => x.SendWelcomeEmailAsync(It.IsAny<string>()),
        Times.Never);
}
```

Test này kiểm tra ba behavior:

1. Nếu email tồn tại, service ném exception.
2. Không được lưu user mới.
3. Không được gửi email.

Đây là ví dụ kết hợp **state/exception verification** với **interaction verification**.

### **6.3. Test case 2 — Đăng ký thành công**

```
[Fact]
public async Task RegisterAsync_ShouldSaveUserAndSendEmail_WhenEmailIsAvailable()
{
    // Arrange
    var repositoryMock = new Mock<IUserRepository>();
    var emailMock = new Mock<IEmailService>();

    repositoryMock
        .Setup(x => x.ExistsByEmailAsync("john@gmail.com"))
        .ReturnsAsync(false);

    var service = new UserService(
        repositoryMock.Object,
        emailMock.Object);

    // Act
    await service.RegisterAsync(
        new RegisterRequest("john@gmail.com"));

    // Assert
    repositoryMock.Verify(
        x => x.AddAsync(
            It.Is<User>(u => u.Email == "john@gmail.com")),
        Times.Once);

    emailMock.Verify(
        x => x.SendWelcomeEmailAsync("john@gmail.com"),
        Times.Once);
}
```

Ở ví dụ này, chúng ta không kiểm tra SQL Server có thực sự lưu user hay không.

Chúng ta chỉ kiểm tra logic của `UserService`.

### **6.4. Hiểu AAA Pattern**

Trong cả hai test trên, ta sử dụng **Arrange – Act – Assert**.

**Arrange**

Chuẩn bị input, dependency, mock

**Act**

Thực thi method cần test

**Assert**

Kiểm tra kết quả mong đợi

Setup → Execute → Verify

Việc chia test thành ba phần giúp đọc và debug dễ hơn, đặc biệt khi test trở nên phức tạp.

## **7. Best Practices trong Unit Test — Chuẩn Production**

### **7.1. Test behavior, không test implementation details**

Đây là một trong những nguyên tắc quan trọng nhất.

Giả sử có method:

```
public decimal CalculateTotal(Order order)
{
    return order.Items.Sum(x => x.Price * x.Quantity);
}
```

Bạn nên kiểm tra tổng tiền trả về có đúng không.

Không nên cố kiểm tra method có sử dụng LINQ `Sum`, `foreach` hay một private helper nào đó.

Lý do là implementation có thể thay đổi, nhưng behavior phải giữ nguyên.

**Unit Test tốt cho phép refactor implementation mà không cần sửa test nếu requirement không thay đổi.**

### **7.2. Mỗi test nên tập trung vào một behavior**

Ví dụ không tốt:

```
[Fact]
public async Task TestUser()
{
    // Test register
    // Test login
    // Test update profile
    // Test delete
}
```

Nếu thất bại, rất khó xác định behavior nào sai.

Nên chia thành các test có mục đích rõ ràng.

Lưu ý: Một behavior có thể cần nhiều assertion để xác nhận tính đúng đắn. Không nhất thiết mỗi test chỉ có một lệnh `Assert`.

### **7.3. Đặt tên test rõ ràng**

Convention thường dùng:

`MethodName_ShouldExpectedBehavior_WhenCondition`

Ví dụ:

```
RegisterAsync_ShouldThrow_WhenEmailAlreadyExists
Withdraw_ShouldFail_WhenBalanceIsInsufficient
AssignPermission_ShouldReject_WhenPermissionAlreadyAssigned
```

Khi test fail trên CI, Developer có thể hiểu ngay tình huống bị lỗi mà không cần mở code.

### **7.4. Không mock mọi thứ**

Đây là lỗi phổ biến.

Giả sử `OrderService` sử dụng một `DiscountCalculator` thuần C#, không có database hay external service.

Bạn có thể sử dụng `DiscountCalculator` thật khi test `OrderService`, nếu điều đó giúp test đơn giản và đáng tin cậy hơn.

Không cần phải tạo interface cho mọi class chỉ để mock.

**Nguyên tắc:** Ưu tiên mock tại những ranh giới với hệ thống ngoài hoặc những dependency khó kiểm soát, thay vì mock tất cả các class trong application.

### **7.5. Không phụ thuộc database thật trong Unit Test**

Không nên yêu cầu Developer phải khởi động SQL Server chỉ để chạy một Unit Test của `UserService`.

Thay vào đó, hãy mock repository hoặc sử dụng Fake phù hợp.

Nhưng nếu mục tiêu là kiểm tra EF Core query, transaction, concurrency hoặc unique constraint, hãy viết Integration Test với database phù hợp.

Đặc biệt, EF Core InMemory không thay thế hoàn toàn SQL Server hay PostgreSQL trong việc xác minh database behavior.

### **7.6. Tránh test private method trực tiếp**

Ví dụ:

```
private bool IsValidEmail(string email)
{
    // Validation logic
}
```

Nếu private method chỉ phục vụ `RegisterAsync`, hãy test qua public behavior của `RegisterAsync`.

Nếu logic có độ phức tạp cao và cần được kiểm tra độc lập, cân nhắc tách nó ra một component có trách nhiệm rõ ràng.

Không nên thay đổi access modifier chỉ để có thể gọi private method trong test.

### **7.7. Tránh dùng Thread.Sleep**

Không tốt:

```
Thread.Sleep(3000);
Assert.True(service.IsCompleted);
```

Test sẽ chậm và có thể không ổn định trên CI.

Nên sử dụng async synchronization, dependency giả hoặc một abstraction để kiểm soát thời gian và việc hoàn thành tác vụ.

### **7.8. Không viết logic phức tạp trong test**

Test cũng là code và có thể chứa bug.

Ví dụ, nếu production code tính discount theo một công thức, không nên sao chép nguyên công thức đó vào Unit Test để tạo expected result.

Hai đoạn code có thể mắc cùng một lỗi và test vẫn pass.

Nên dùng input đơn giản và expected result được xác định độc lập.

### **7.9. Không chạy test dựa trên dữ liệu chung có thể thay đổi**

Tránh dùng chung mutable static state hoặc dùng một database record mà nhiều test cùng sửa.

Nếu test cần dữ liệu, hãy tạo dữ liệu riêng cho test đó.

Điều này giúp tránh tình trạng:

> Chạy từng test thì pass, chạy cả test suite thì fail.

### **7.10. Kiểm tra exception đúng loại**

Không nên chỉ kiểm tra method có ném exception bất kỳ.

Hãy kiểm tra loại exception cụ thể và thông tin lỗi có ý nghĩa nếu đó là một phần contract của service.

Ví dụ:

```
await Assert.ThrowsAsync<InvalidOperationException>(
    () => service.RegisterAsync(request));
```

Tránh `catch (Exception)` rồi coi như test pass vì bất kỳ lỗi nào cũng có thể khiến test thành công.

### **7.11. Sử dụng Theory cho nhiều bộ dữ liệu**

Trong xUnit, `[Fact]` phù hợp với một scenario cố định.

`[Theory]` phù hợp khi bạn muốn kiểm tra cùng một behavior với nhiều input.

```
[Theory]
[InlineData(-1)]
[InlineData(0)]
[InlineData(-100)]
public void Withdraw_ShouldThrow_WhenAmountIsNotPositive(
    decimal amount)
{
    var account = new BankAccount(1000);

    Assert.Throws<ArgumentOutOfRangeException>(
        () => account.Withdraw(amount));
}
```

Đây là cách tốt để viết các boundary test.

### **7.12. Có chiến lược Code Coverage hợp lý**

Không nên chỉ đặt mục tiêu 100% coverage.

Ví dụ:

| Thành phần                 | Mức ưu tiên Unit Test     |
| -------------------------- | ------------------------- |
| Business rules             | Rất cao                   |
| Pricing, Discount          | Rất cao                   |
| Authorization decisions    | Rất cao                   |
| State transitions          | Rất cao                   |
| Application Services       | Cao                       |
| Controllers chỉ điều hướng | Thấp hơn                  |
| EF Core mapping            | Ưu tiên Integration Test  |
| Repository SQL queries     | Ưu tiên Integration Test  |
| External API contracts     | Integration/Contract Test |

Nếu team đặt coverage threshold, hãy xem đó là công cụ hỗ trợ kiểm soát chất lượng, không phải thước đo duy nhất.

## **8. Unit Test và Integration Test trong real production**

Một ứng dụng ASP.NET Core thường cần nhiều cấp độ kiểm thử.

| Tiêu chí            | Unit Test            | Integration Test         | E2E Test                        |
| ------------------- | -------------------- | ------------------------ | ------------------------------- |
| Mục tiêu            | Logic/hành vi đơn vị | Nhiều component phối hợp | Luồng người dùng hoàn chỉnh     |
| Database thật       | Thường không         | Có thể                   | Thường có                       |
| Tốc độ              | Nhanh                | Trung bình               | Chậm hơn                        |
| External dependency | Thay thế/kiểm soát   | Có thể dùng thật         | Thường dùng môi trường tích hợp |
| Ví dụ               | Kiểm tra discount    | Test API + SQL Server    | Register → Login → Checkout     |

Microsoft cũng hướng dẫn sử dụng integration testing trong ASP.NET Core với test host để kiểm tra các thành phần phối hợp với nhau.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://learn.microsoft.com\&sz=32)

Microsoft Learn+1



### **Ví dụ: API gán Permission vào Role**

Giả sử bạn có API:

```
POST /api/roles/1/permissions/5
```

**Unit Test phù hợp để kiểm tra:**

- Role không tồn tại → trả về business error.
- Permission không tồn tại → trả về business error.
- Permission đã được gán → không cho gán trùng.
- Permission hợp lệ → gọi repository để thêm quan hệ.

**Integration Test phù hợp để kiểm tra:**

- Bảng `RolePermissions` lưu dữ liệu đúng.
- Composite key `{ RoleId, PermissionId }` ngăn dữ liệu trùng.
- Foreign key được enforce đúng.
- Transaction rollback khi có lỗi.
- Hai request đồng thời có làm phát sinh conflict hay không.

Đây là lý do một Senior Developer không chỉ hỏi “Đã viết Unit Test chưa?” mà còn hỏi “Rủi ro này nên được kiểm chứng ở test level nào?”.

## **10. Tình huống Production: Khi nào nên viết Unit Test?**

Giả sử bạn được giao một user story:

> Admin có thể revoke một permission khỏi role. Nếu role hoặc permission không tồn tại, hệ thống trả về lỗi phù hợp. Nếu permission chưa được gán, hệ thống phải xử lý theo business rule được thống nhất.

Cách tiếp cận phù hợp:

**Bước 1 — Phân tích business rule**

Xác định những behavior cần được đảm bảo, bao gồm cả quyền của người gọi và trường hợp dữ liệu đã bị thay đổi.

**Bước 2 — Lập danh sách test case trước khi code**

Ví dụ:

```
RevokePermission_ShouldFail_WhenRoleDoesNotExist
RevokePermission_ShouldFail_WhenPermissionDoesNotExist
RevokePermission_ShouldFail_WhenPermissionIsNotAssigned
RevokePermission_ShouldRemovePermission_WhenAssignmentExists
RevokePermission_ShouldNotSave_WhenValidationFails
```

Lưu ý: Nếu requirement quy định revoke một permission chưa được gán phải là idempotent success, test case thứ ba cần thay đổi tương ứng.

**Bước 3 — Implement business logic**

Đặt logic tại Application Service hoặc Handler phù hợp với kiến trúc, không nhồi toàn bộ vào Controller.

**Bước 4 — Viết Unit Test**

Mock các dependency liên quan, chuẩn bị dữ liệu và kiểm chứng business outcome.

**Bước 5 — Viết Integration Test cho rủi ro về database**

Ví dụ, kiểm tra truy vấn cập nhật, foreign key, transaction và concurrent requests.

**Bước 6 — Chạy test trên CI**

Yêu cầu test pass trước khi merge pull request theo chính sách của team.

## **11. Checklist tự đánh giá Unit Test**

Bạn có thể sử dụng checklist này khi code review hoặc trước khi tạo pull request.

**Production Unit Test Review**

0/12 hoàn thành

Tên test mô tả rõ behavior và điều kiện

Test sử dụng Arrange – Act – Assert

Expected result được xác định độc lập với implementation

Không mock những dependency không cần mock

Không verify internal method calls không liên quan contract

Test có assertion rõ ràng, có ý nghĩa

Test chạy ổn định và đủ nhanh trên CI

Không dùng coverage percentage làm thước đo duy nhất

## **13. Tổng kết — Tư duy của Senior Developer về Testing**

Khi làm việc trong production, mục tiêu không phải là viết càng nhiều Unit Test càng tốt, mà là **đảm bảo các behavior quan trọng được kiểm chứng bằng loại test phù hợp, với chi phí bảo trì hợp lý**.

Một Developer có kinh nghiệm nên hiểu rõ:

- Unit Test giúp bảo vệ business rules và giảm regression bug.
- Unit Test phải độc lập, nhanh, ổn định và dễ đọc.
- Fake, Stub và Mock là những cách khác nhau để thay thế dependency.
- Không nên mock mọi thứ hoặc test quá sâu vào implementation details.
- Unit Test không thể thay thế Integration Test, đặc biệt với database, transaction, concurrency và external systems.
- Coverage là một tín hiệu tham khảo, không phải bằng chứng code không có bug.

**Tư duy quan trọng nhất:** Trước khi viết test, hãy xác định *behavior nào thực sự cần được bảo vệ, rủi ro gì có thể xảy ra và loại test nào sẽ phát hiện rủi ro đó tốt nhất.*
